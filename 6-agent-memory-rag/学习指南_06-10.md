## 一、公共底座：5 个文件共用的知识（先读这节，30 分钟）

### 1.1 唯一需要记住的调用模式

5 个文件里所有工具交互都是同一种写法：

```python
tool.run({"action": "xxx", ...参数})
```

- `MemoryTool` 的 action：`add` / `search` / `summary` / `stats` / `forget` / `consolidate`
- `RAGTool` 的 action：`add_document` / `add_text` / `search` / `ask` / `stats` / `clear`

这是整个框架的**统一工具接口**：不管底层多复杂（SQLite、Qdrant、Neo4j、嵌入模型、LLM），对外就是一个 `run(字典)` 进、一个字符串出。08 的 `ToolRegistry` 就是为了让 Agent 能统一发现和调用这些工具。

### 1.2 数据都存在哪

| 数据 | 位置 | 生命周期 |
|---|---|---|
| 工作记忆 | **纯内存**（进程内的 List） | 进程退出即消失 |
| 情景/语义记忆 | SQLite（`memory_data/memory.db`）+ Qdrant + Neo4j | 持久 |
| 感知记忆 | SQLite + Qdrant 独立集合（文本 384 / 图像 512 / 音频 512 维） | 持久 |
| RAG 分块 | Qdrant 独立集合 `hello_agents_rag_vectors`（384 维 cosine） | 持久 |
| RAG 的"知识库目录" | `./xxx_kb/`（只是 add_text 的临时文件中转站，用完即删） | — |

### 1.3 四个全局坑（每个示例都会撞上）

| # | 坑 | 现象 | 说明 |
|---|---|---|---|
| 1 | **namespace 不传就落 default** | 07 构造传了 `intelligent_qa_demo`，日志却显示"命名空间: default" | `run()` 里所有 action 的 namespace 默认 `"default"`，构造参数只影响初始化。04/07 的数据都写在 default 里，**互相污染**。想隔离：每次 run 显式传 `"namespace": "xxx"` |
| 2 | **数据跨运行累积** | stats 数字越跑越大 | consolidate/add 不查重，反复跑同一示例数据会堆叠（importance 还会 ×1.1 递增） |
| 3 | **stats 口径是"集合总点数"** | stats 显示的分块数 > 本次脚本写入数 | 数的是整个 Qdrant 集合的历史总量，不是本次新增 |
| 4 | **清库才能干净复现** | — | 删 Qdrant 集合 + 删 `memory_data/` 目录（具体命令见 README 坑位表） |

## 二、06 记忆整合：从"临时便签"到"长期档案"

> 难度 ★☆☆☆☆ · 不需要 LLM · 约 2 分钟跑完

### 2.1 一句话 + 生活类比

06 只教一件事：**`consolidate`（整合）**——把重要的工作记忆转成长期记忆。

类比：工作记忆是桌上的**便签**（最多 10 张，过夜就扔），episodic 是**日记本**，semantic 是**百科全书**。整合 = 每天晚上把重要的便签抄进日记本，反复出现的知识提炼进百科全书。

### 2.2 跑之前，预判会发生什么

1. 先 add 8 条工作记忆（importance 从 0.2 到 0.9 不等）
2. 第一次整合（阈值 0.6）：importance ≥ 0.6 的记忆被转成 episodic，且 importance 变成原值 × 1.1
3. 第二次整合（阈值 0.8）：只剩高重要性的被转
4. 最后统计 + 按 memory_type 搜索验证

### 2.3 逐方法导读

| 方法 | 干什么 | 关键点 |
|---|---|---|
| `setup_initial_memories` | add 8 条 working 记忆 | 注意 `memory.pop("content")` 的写法：content 和 importance 被 pop 出来单独传，**剩下的字典直接 `**` 展开进 run()**——这就是"附加元数据"的传递方式 |
| `demonstrate_consolidation_criteria` | 讲"整合标准" | ⚠️ 纯 print 演示（见 2.5），跑不跑无所谓 |
| `demonstrate_consolidation_process` | 真正执行两次 consolidate | 观察 stats 前后变化；`from_type/to_type/importance_threshold` 三个参数都在这里 |
| `demonstrate_consolidation_metadata` | 验证元数据是否保留 | add 一条带特殊元数据的记忆 → 整合 → 搜索验证元数据还在 |
| `demonstrate_multi_type_consolidation` | 三条整合路径 | working→episodic、working→semantic、episodic→semantic |
| `demonstrate_consolidation_benefits` | 收尾统计 | 跨类型检索测试 |

### 2.4 深入一层：consolidate 在框架里做了什么

源码位置：`.venv/Lib/site-packages/hello_agents/memory/manager.py` 的 `consolidate_memories()`（L220 起）

```
1. 检查 from_type / to_type 是否都在本工具启用的 memory_types 里（不在 → 只打 warning，返回 0）
2. 从源类型的内存列表取全部记忆，按 importance >= 阈值 筛选
3. 逐条复制到目标类型：importance × 1.1，memory_type 改为目标类型
4. 不查重 —— 同一条记忆每整合一次就多一份、importance 再乘一次 1.1
```

两个推论（跑多了就能观察到）：
- **为什么搜索里会出现 0.77 这种值**：0.7 × 1.1 = 0.77
- **工作记忆是纯内存的**：脚本跑完进程退出，working 就没了；episodic/semantic 在库里持久。所以"整合"的语义就是"趁进程还活着，把内存里的东西落盘"

### 2.5 话术 vs 实际

| 脚本说 | 实际 |
|---|---|
| "整合标准演示"分析不同阈值 | 该方法里 `working_memories = []` 是**空列表死代码**，循环里只 print 不分析 |
| "整合后的情景记忆"（`query=""` 空查询） | 空查询的搜索结果不可靠，要看真实效果用带关键词的 search |
| 整合后"释放工作记忆空间" | consolidate 是**复制不是移动**，源记忆不会被删；真正删要用 `forget` |

### 2.6 动手练习

1. **改阈值**：把 `consolidation_tests` 的两个阈值改成 0.3 和 0.95，观察整合条数变化
2. **验证 ×1.1**：加一条 importance=0.5 的记忆，用阈值 0.5 整合后搜索它，看显示的 importance 是不是 0.55
3. **验证累积**：连续跑两遍 06，第二遍 stats 里 episodic 数量约翻倍——然后按 README 清库，再跑一遍对照

## 三、09 四种记忆类型深挖：记忆系统的"四室一厅"

> 难度 ★★★☆☆（篇幅最长，但概念不比 06 难）· 不需要 LLM

### 3.1 一句话

09 把 MemoryTool 拆成 **4 个只启用单一类型的独立实例**，分别演示 working / episodic / semantic / perceptual 各自的脾气，最后演它们怎么配合。

### 3.2 四类型总表（本文最重要的表）

| 类型 | 类比 | 实际容量 | 存储 | 检索方式 | 适合存 |
|---|---|---|---|---|---|
| working | 桌上便签 | **10 条**（TTL 120 分钟） | 纯内存 | TF-IDF×0.7 + 关键词×0.3，再乘时间衰减和重要性权重 | 当前任务的临时状态 |
| episodic | 日记本 | 100 条 | SQLite + Qdrant | 向量相似度 | 带时间线的事件、经历 |
| semantic | 百科全书 | 100 条 | Qdrant + Neo4j | 向量相似度 + 图谱 | 概念、定义、关系 |
| perceptual | 相册/录音柜 | 100 条 | SQLite + Qdrant×3（按模态分集合） | 按模态的向量相似度 | 图像/音频/文本的感知内容 |

> 脚本宣称工作记忆"默认 50 条"是**错的**——框架源码 `memory/base.py` L39：`working_memory_capacity: int = 10`。

### 3.3 逐方法导读

| 方法 | 干什么 | 值得看的地方 |
|---|---|---|
| `demonstrate_working_memory` | 容量、TTL、快速检索、清理 | `forget` + `importance_based` 策略（阈值 0.4 以下的被硬删） |
| `demonstrate_episodic_memory` | 事件序列、丰富上下文、记忆链条 | 5 步学习会话用 `session_id + sequence_number` 串联——这是"时间线"的正确打开方式 |
| `demonstrate_semantic_memory` | 概念、关系、知识图谱 | 注意元数据里的 `parent_concept` / `subject` / `object` / `relation_type`——关系型知识的结构化写法 |
| `demonstrate_perceptual_memory` | 文本/图像/音频三模态 | 图像和音频都是**模拟数据**（`/simulated/...` 假路径），见 3.5 |
| `demonstrate_memory_interactions` | 四类型协作的完整学习流程 | 感知→工作→情景→语义，最后跨类型检索同一个 query |

### 3.4 深入一层：为什么要用 4 个独立实例？代价是什么？

脚本为每种类型单独建了 `MemoryTool(memory_types=["xxx"])`，意图是隔离演示。但注意代价：

- **每个实例的 memory_types 字典里只有一种类型** → 跨类型的 `consolidate`（如 working→episodic）在单类型工具上会命中源码 L236 的检查：`to_type not in self.memory_types` → **只打一条 warning，静默返回 0，什么都没发生**
- 所以 3.3 表格里 `demonstrate_memory_interactions` 第 5 步的"工作记忆整合"，在这个脚本里**实际是空转**（日志里能看到 warning）
- 想看真正的跨类型整合，回到 06（它启用了全部 4 种类型）

### 3.5 话术 vs 实际

| 脚本说 | 实际 |
|---|---|
| 工作记忆"默认 50 条" | **10 条**（base.py `working_memory_capacity=10`） |
| TTL 演示"模拟 5/10/30 分钟前" | `simulated_age_minutes` 只是存进元数据的一个数字，**不会修改记忆的真实时间戳**，对过期和衰减没有影响 |
| "记忆链条构建"（parent_memory） | 链条 ID 是 `f"{chain_type}_memory"` 拼出来的**假 ID**（代码注释自己写了"简化处理"），检索时并不能沿链条回溯 |
| 图像/音频感知记忆 | 路径是 `/simulated/xxx`，实际入库的只有 content 文本和它的**文本嵌入**；只有传入真实文件路径才会触发 CLIP（图像 512 维）/ CLAP（音频 512 维）多模态嵌入 |
| 第 5 步"记忆整合演示" | 单类型工具上跨类型 consolidate **静默返回 0**（见 3.4） |

### 3.6 动手练习

1. **验证容量**：往 working 工具连加 15 条，stats 看是否只有 10 条（超过的被挤掉）
2. **对照四类型检索**：用同一个 query（如"深度学习"）分别搜 4 个工具，体会同词在不同类型库里的召回差异
3. **修复整合空转**：把 `demonstrate_memory_interactions` 里的 consolidate 挪到一个启用 `["working","episodic"]` 两种类型的工具上执行，确认返回值 > 0

## 四、07 RAG 智能问答：让 AI"开卷考试"

> 难度 ★★☆☆☆ · 需要 LLM · 全脚本约 65 次 LLM 调用，跑完约 6-7 分钟

### 4.1 一句话 + 类比

07 教的是 `ask`：**先检索相关片段，再把片段塞进 prompt 让 LLM 作答**。类比"开卷考试"——LLM 不靠记忆瞎答，而是看着参考资料（你的知识库）作答，还把引用页码（相似度+来源）标在卷尾。

### 4.2 ask 的六步流水线（核心，务必掌握）

```
问题 ──► ① 查询扩展（MQE：LLM 生成 2 个改述；HyDE：LLM 写一段假设答案）  ← 2 次 LLM
      ──► ② 多路向量检索（原问题+2 改述+1 假设答案，共 4 个查询各嵌一次、各查一次 Qdrant，合并去重取 top-k）
      ──► ③ 上下文构建（每片段压平截 300 字；总量超 max_chars=1200 时按段落断点截断）
      ──► ④ 提示词组装（system prompt 框架里写死；user prompt = 问题 + 片段列表）
      ──► ⑤ LLM 生成答案                                                    ← 第 3 次 LLM
      ──► ⑥ 格式化输出（答案 + "参考来源"列表 + 检索/生成耗时）
```

**一次 ask = 3 次 LLM 调用**。日志里每个问题前的 4 条 `Batches:` 进度条就是第②步的 4 次嵌入。

### 4.3 逐方法导读

| 方法 | 干什么 | 关键点 |
|---|---|---|
| `_setup_knowledge_base` | 3 篇 markdown 知识入库 | 又是 add_text 的临时文件方案；构造传的 namespace 没生效（坑 #1） |
| `demonstrate_question_understanding` | 4 类问题 × 2 个逐个 ask | 单次 14~26 秒；"问题分类"只是把问题按类别组织，**没有分类逻辑** |
| `demonstrate_context_construction` | 先 search 看片段，再 ask 看全链路 | `max_chars=1500` 在这里覆盖默认 1200 |
| `demonstrate_answer_quality_analysis` | 3 个难度问题 + 自制评分 | 评分公式见下 |
| `demonstrate_prompt_engineering` | 3 种提示词策略"对比" | ⚠️ 假演示，见 4.4 |
| `demonstrate_citation_system` | 开/关引用对比 | `include_citations` 参数是真实生效的（区别于提示词） |

质量评分公式（`_calculate_quality_score`，**脚本自制、非框架能力**）：
内容关键词命中 40% + 长度 30%（满 500 字得满分）+ 有"参考来源"字样 20% + 速度 10%（1 秒满分、6 秒以上 0 分）。

### 4.4 话术 vs 实际（本文件实测 5 条）

| 脚本说 | 实际 |
|---|---|
| 构造传 `rag_namespace="intelligent_qa_demo"` | 全落 default，且**检索结果混进了 04 写入的残留数据**（思考过程里出现 memory_types 表格内容） |
| 回答正文 | **`<think>...</think>` 思考过程混在答案最前面**（MiniMax 是推理模型，框架未过滤），预览/长度统计被污染 |
| "提示词工程"对比 3 种策略 | 3 个 system_prompt **根本没传入**（循环里固定调 ask），同一问题跑 3 遍；框架也不支持外部传 system prompt |
| "包含 N 个引用来源" | `answer.count("参考来源")` 恒等于 **1**（只数尾部格式化那一次出现），不是引用条数 |
| 质量评分 9/10 很可信 | 关键词匹配极粗糙（"定义""应用"这类词几乎必含），长度分被思考过程灌水 |

### 4.5 动手练习

1. **隔离数据**：所有 run 都加 `"namespace": "qa_demo"`（add 和 ask 都要传），重跑后对比检索质量——思考过程里不再出现 04 的残留内容
2. **关闭高级检索省钱**：ask 时传 `"enable_advanced_search": False`，对比耗时（会从 ~20 秒降到 ~10 秒以内，代价是检索召回略降）
3. **看引用格式**：ask 一个库里明确有的问题（如"SOLID 原则"），观察"参考来源"的三档相似度 emoji（🟢>0.8 / 🟡>0.6 / 🔵其余）

## 五、10 RAG 完整管道：一条流水线的全景图

> 难度 ★★★☆☆ · 需要 LLM · 调用量很大（粗算 100+ 次 LLM），**跑完整脚本可能要 10 分钟以上**；建议分段跑（把 main 里不看的 demo 注释掉）

### 5.1 一句话

10 是 04（摄取）+ 05（检索）+ 07（问答）的**总装车间**：5 个 demo 对应管道的 5 个阶段，把前面学过的零件装成一台完整的机器。

### 5.2 五阶段与已学示例的对应

| demo（阶段） | 对应已学 | 新增内容 |
|---|---|---|
| `demonstrate_document_ingestion` | 04 的 add | 带元数据的批量摄取 |
| `demonstrate_chunking_strategies` | 04 的分块 | 长文档（AI 发展史）+ 结构化文档（算法手册）的分块对照 |
| `demonstrate_advanced_retrieval` | 05 的高级检索 | ⚠️ 大量"手动模拟"，见 5.4 |
| `demonstrate_intelligent_qa` | 07 的 ask | 5 类问题 + 多轮对话 |
| `demonstrate_performance_optimization` | 04 的性能测试 | ⚠️ 假对比，见 5.4 |

### 5.3 值得细看的两处

- **多轮对话**（`demonstrate_intelligent_qa` 第 3 小节）：后续问题手动拼上前文关键词（`f"卷积神经网络 {question}"`）。这是**真知识**：RAG 本身无状态，多轮对话的上下文要调用方自己维护——这正是后面 Agent 记忆系统要解决的问题
- **HyDE 的直觉**（`demonstrate_advanced_retrieval` 第 2 小节）：手写一段"假设答案"去检索，比用问题本身检索更容易命中正文。看懂这个小节 = 理解了 HyDE 的动机

### 5.4 话术 vs 实际（本文件最多，读代码时别被绕晕）

| 脚本说 | 实际 |
|---|---|
| MQE 演示：手写 4 个扩展查询再逐个 search | 框架的 search **默认自动**做 MQE+HyDE（每次 search 本来就是 3 次 LLM + 4 路检索）。手写一遍的价值是理解原理，但注意每个手写查询又触发了框架自己的扩展 |
| 重排序：权重 0.6/0.2/0.2 | 纯 print；"重排序后结果"和初始结果是**同一查询再跑一遍**（limit 8→5 而已），排序没有任何变化 |
| 缓存机制：第二次查询更快 | 框架**没有缓存**；第二次快只是模型/连接预热 |
| 单个处理 vs 批量处理性能对比 | 两段**一模一样的 for 循环**跑两遍，"性能提升 xx%"无意义 |
| 系统监控：15 个文档/2.5MB/128MB | 全部**硬编码的假数字**，与你的实际环境无关 |

### 5.5 动手练习

1. **分段跑**：main 里只留 `demonstrate_chunking_strategies`，观察长文档分了几个块（提示：AI 发展史那篇在 800 token 上限下不止 1 块，与 04 的单块现象形成对照）
2. **改造假缓存为真缓存**：在脚本里加一个 `dict`，query 相同直接返回上次结果——体会"缓存该做在哪一层"
3. **测量真实成本**：给每次 run 前后计时，统计全程 LLM 相关耗时占比，建立"哪些 action 贵"的直觉（贵：search/ask；便宜：add/stats）

## 六、08 工具集成：两条线的汇合，通往真正的 Agent

> 难度 ★★☆☆☆ · 概念最少，但"下一步"价值最大

### 6.1 一句话

08 演示框架的集成层：`ToolRegistry` 统一注册工具，`SimpleAgent` 拿着工具表干活。MemoryTool 和 RAGTool 在这里第一次同框。

### 6.2 逐方法导读

| 方法 | 干什么 | 关键点 |
|---|---|---|
| `setup_agent` | 初始化两个工具 → 注册 → 创建 SimpleAgent | Agent 三件套：`name` + `llm` + `system_prompt`，外加 `tool_registry` |
| `demonstrate_tool_registry_pattern` | 注册/发现/获取工具 | `list_tools()` / `get_tool("memory")`；注意访问了 `_tools` 私有属性（演示用途，不推荐模仿） |
| `demonstrate_unified_interface` | 用同一个 `run({"action":...})` 调两个工具 | 这就是 1.1 讲的统一接口的价值 |
| `demonstrate_collaborative_workflow` | 4 个场景：学习→回顾→应用→分析 | 每个场景都是"RAG 存知识 + Memory 记事件"的**固定套路**——这是最值得背下来的模式 |
| `demonstrate_agent_orchestration` | "复杂任务编排" | ⚠️ 见 6.3 |
| `demonstrate_performance_analysis` | 两工具性能计时 | 纯计时，无坑 |

### 6.3 最大的"话术 vs 实际"：Agent 创建了，但从未运行

通读 08 你会发现：`self.agent` 创建之后，**整个脚本没有一处 `agent.run(...)`**。所有"编排""协同"都是脚本手工顺序调用 `tool.run()`——是你（脚本作者）在编排，不是 Agent 在编排。

`demonstrate_agent_orchestration` 的"4 步编排"实际是 4 行手写的工具调用。真正的"Agent 自主编排"应该是：给 Agent 一句话目标，它自己决定调哪个工具、调几次。

### 6.4 SimpleAgent 真正的工作原理（进阶必读）

源码：`.venv/Lib/site-packages/hello_agents/agents/simple_agent.py`

```
agent.run("你的问题")
  ├─ 1. 把"可用工具清单 + 调用格式"注入 system prompt
  ├─ 2. LLM 生成回答
  ├─ 3. 用正则从回答文本里找 [TOOL_CALL:工具名:参数] 标记
  ├─ 4. 找到 → 解析参数 → tool.run() → 把结果作为新消息回填 → 回到 2
  └─ 5. 没找到 → 这就是最终回答
  （工具循环最多 3 轮：max_tool_iterations=3）
```

两个值得注意的设计：
- 工具调用**不是** OpenAI function calling，而是约定文本标记 `[TOOL_CALL:...]`——LLM 只要会"照格式写字"就能调工具
- 参数解析很宽容：支持 JSON、`key=value` 逗号分隔、纯文本自动推断 action（如给 memory 传纯文本 → 自动当 search 的 query）

### 6.5 动手练习：让 Agent 真的跑起来（08 没做的事）

在 08 的 main 末尾加：

```python
response = demo.agent.run(
    "帮我把这句话记住（存成情景记忆，重要性0.8）："
    "今天学习了HelloAgents的工具集成，然后用一句话告诉我你刚才用了哪个工具。"
)
print(response)
```

观察要点：
1. 回答里是否出现 `[TOOL_CALL:memory:...]` 样式的中间过程
2. Agent 是否真的调了 MemoryTool（跑完后用 `demo.memory_tool.run({"action":"search","query":"工具集成","limit":3})` 验证落库）
3. 再问它一个知识库问题（如"观察者模式是什么"），看它会不会**自己选择**改调 RAGTool——这才是"编排"的本义
