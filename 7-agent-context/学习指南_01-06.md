### P5. 「笔记 → 上下文」这条注入链路在 0.2.9 上是断的（三处独立原因）

`codebase_maintainer.py::run()` 里有一段看着很关键的逻辑：检索笔记 → `_notes_to_packets()` 转成 `ContextPacket`
→ 塞进 `additional_packets` → 交给 `ContextBuilder.build()`。**实测这条链路的产出一个字都进不了最终上下文。**
三层原因各自独立，任意一层都足以让它失效：

**① 结构性丢弃 —— `type="note"` 这个取值 `_structure()` 根本不认**
`_notes_to_packets()` 设的是 `metadata={"type": "note", ...}`，而 `builder.py::_structure()` 只渲染上表列出的那几种 type。
`builder.py` 全文**没有出现过 "note" 这个词**（`grep -n note` 零命中）→ note 包没有分支可走，直接消失。

**② 相关性被静默重算 —— 预设分数被覆盖成「空格分词重叠率」**
`_select()` L211–217 对**所有** packet 无条件重算：

```python
query_tokens = set(user_query.lower().split())          # 按空格切词
packet.relevance_score = overlap / len(query_tokens)
```

`codebase_maintainer.py` 里那份 `relevance_map = {"blocker": 0.9, "action": 0.8, ...}` 就此被彻底丢弃。
中文句子没有空格，整句算一个 token，重叠率几乎恒为 0 → 一律低于 `min_relevance=0.2` 被滤掉。
实测：预设 `relevance_score=0.9` 的包，重算后为 `0.00`。

**③ 记忆通路调用了不存在的方法**
`builder.py:143,156` 写的是 `self.memory_tool.execute("search", query=..., min_importance=0.7, limit=5)`，
但 `MemoryTool` 只有 `run(parameters: dict)`（`tools/base.py` 里也没有 `execute`）。运行时静默走 except：

```
⚠️ 记忆检索失败: 'MemoryTool' object has no attribute 'execute'
```

注意同一个文件里 `rag_tool` 的写法是**对的**（L172 用 `run({"action": "search", ...})`）—— 两种调用风格并存，典型的历史遗留。

**合起来看**：`[State]` 永远为空（③ 导致记忆包收集不到），`[Evidence]` 拿不到笔记（①②）。
那为什么跨会话演示看起来还能用？因为笔记的跨会话能力实际走的是**工具**这条路 ——
Agent 自己调 `note.list` / `note.search`，压根不依赖上下文注入。
也就是说 `codebase_maintainer.py` 里那段「笔记注入上下文」目前是装饰性的。

**实测验证过的修复配方**（两处都要改，缺一不可）：

```python
# 1) metadata 的 type 换成 _structure 认识的值
metadata={"type": "tool_result", "note_type": note_type, "note_id": ...}   # 原为 "note"
# 2) 相关性阈值降到 0，否则中文查询会被空格分词机制整体滤掉
ContextConfig(max_tokens=4000, reserve_ratio=0.15, min_relevance=0.0, enable_compression=True)
```

改后实测渲染结果（`additional_packets` 塞一张 blocker 笔记）：

| metadata.type | `min_relevance` | 渲染出的分区 |
|---|---|---|
| `note` | 0.2 / 0.0 | 三段恒定分区（**结构性丢弃，改阈值也无效**） |
| `tool_result` / `retrieval` | 0.2 / 0.0 | 前者无变化；后者多出 `[Evidence]` |
| `task_state` | 0.0 | 多出 `[State]` |
| `history` | 0.0 | 多出 `[Context]` |

> 本地**没有**改动这段逻辑，刻意保持与上游一致。想让它真正生效，按上面两处自行修改即可
> （`min_relevance=0.0` 会让所有包都参与预算竞争，注意 `max_tokens` 是否够用）。

### `04_note_tool_integration.py`｜9.4.4
三个值得注意的实现细节：
1. `_ensure_list_of_dicts()`（L117）——一大坨防御式解析，因为 NoteTool 返回值可能是 `str`/`dict`/`list`/`{"items":[...]}` 四种形态，说明接口契约不严。
2. `_notes_to_packets()` 里 `relevance_score` 硬编码 `0.75`，与 `codebase_maintainer.py` 的按类型分级做法不同，可对比阅读。
3. L268–269 `json.dumps(summary, indent=2, ensure_ascii=False).replace("\\n", "\n")` —— 这行是**有意为之的「打印美化」**：把 JSON 字符串值里转义的 `\n` 还原成真实换行，让终端输出可读。
   实测副作用是 **输出不再合法**（`json.loads` 会报 `Invalid control character at: line 2 column 10`）。想程序化消费 `summary` 就不要加这个 `.replace`。

### `05_terminal_tool_examples.py`｜9.5.1 / 9.5.3
五个函数对应五个场景，安全演示部分实测结果：
- `rm -rf /` → `❌ 不允许的命令: rm`，并回显 37 条白名单
- `cat /etc/passwd` → 被沙箱重定向到工作目录内，报 `No such file or directory`
- `cd ../../../etc` → `❌ 不允许访问工作目录外的路径`

每个 `demo_*()` 都新建独立 `TerminalTool` 并切换 `workspace`，这是理解「工作目录沙箱」最直观的写法。

### `06_three_day_workflow.py`｜9.6.4
`day_1_exploration` / `day_2_analysis` / `day_3_planning` / `week_later_review` 四段对应 9.6 的四天节奏，
外加 `demonstrate_cross_session_continuity()` 与 `demonstrate_tool_synergy()`。
所有 prompt 都刻意写得「只给目标、不给步骤」（如「请探索 . 的代码结构」），以体现 **Agent 自主决策** 这一本章升级点。

#### 怎么跑（本地已加阶段选择器）

**必须在本目录下执行**——`NoteTool(workspace=f"./{project_name}_notes")` 是相对路径，换目录跑笔记会落到别处。

```bash
cd 7-agent-context
PY=../.venv/Scripts/python.exe      # 项目根 .venv（Windows）

$PY 06_three_day_workflow.py help      # 先看阶段列表
$PY 06_three_day_workflow.py week      # 再跑这个：0 次 LLM 调用，验证环境是否通
$PY 06_three_day_workflow.py day1      # 正式跑第一天
```

上游 `main()` 是「一次全跑」设计，7 个阶段共 8 次 Agent 调用，每次最多 30 轮工具迭代（`max_tool_iterations=30`）——最坏情况上百次 LLM 请求。**本地加了命令行阶段参数**，可分批跑：

| 阶段 | 内容 | Agent 调用次数 |
|---|---|---|
| `day1` | 探索代码库 | 2 |
| `day2` | 分析代码质量 | 2 |
| `day3` | 规划重构任务（会检索前两天攒下的笔记） | 2 |
| `week` | 笔记摘要 + 会话报告（纯本地） | **0** |
| `cross` | 跨会话连贯性演示 | 1 |
| `synergy` | 三大工具协同演示 | 1 |

- 不传参数 = 全部阶段，行为与上游一致；简写 `1`/`2`/`3`、`days`（=day1+day2+day3+week）、`extra`（=cross+synergy）。
- 多个阶段可任意组合，**执行顺序固定按上表**（避免写成 `day3,day1` 导致笔记为空）。
- `day1`/`day2`/`day3`/`week` 共用同一个 `CodebaseMaintainer` 实例，所以要么一起跑、要么按序跑；单独跑 `day3` 会读到空笔记。
- 笔记落在 `./demo_codebase_notes/`、`./synergy_demo_notes/`，**跨次运行会累积不清空**。要干净复现先 `rm -rf *_notes maintainer_report_*.json`。

#### Windows 专属坑：命令输出非 UTF-8 时会变成一条误导性报错

实测 `day1` 时后台抛过一次 `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xc7`。根因链条（已逐环复现）：

1. 环境里设了 **`PYTHONUTF8=1`**，于是 `locale.getpreferredencoding(False)` 返回 `utf-8`；

   ```
   PYTHONUTF8            = 1
   sys.flags.utf8_mode   = 1
   locale.getencoding()  = cp936                 # 真实系统编码仍是 GBK
   locale.getpreferredencoding(False) = utf-8    # UTF-8 模式把它改掉了
   ```

2. `terminal_tool.py:217–225` 调 `subprocess.run(..., text=True)` **没指定 `encoding=`**，于是按上一步的 utf-8 解码子进程输出；
3. 中文 Windows 下 `cmd` / `dir` / `findstr` 这类命令吐出的是 **GBK 字节**（如 `0xc7`、`0xd6`），解码当场失败，`_readerthread` 线程抛异常；
4. 异常导致 `result.stdout` 为 `None`，接着 L244 的 `len(output)` 抛 `TypeError`，最终被 `_execute_command` 的 `except` 兜住，返回：

   ```
   ❌ 命令执行失败: object of type 'NoneType' has no len()
   ```

**注意两件事**：一是报错信息完全指不到真实原因（跟命令本身毫无关系，Agent 再聪明也只会以为命令写错了）；二是这条报错只作为工具返回值回给 Agent，**不会打到 stdout**，所以翻日志看不见，只能靠观察「Agent 反复试同一个命令」来发现。

规避：让 Agent 尽量走 `ls` / `cat` / `grep` 这些输出 ASCII 或 UTF-8 的命令。真要跑中文输出的命令（`dir`、`findstr`、带中文路径的 `find`），得改框架源码在 `subprocess.run` 里补 `encoding="gbk"`（或用 `errors="replace"` 兜底）。

### `codebase_maintainer.py`｜9.6.3（全章重点）
476 行，直接继承 `FunctionCallAgent` 而非 `SimpleAgent`，这是它与 `04` 的 `ProjectAssistant` 的本质区别：

```python
self.memory_tool = MemoryTool(user_id=project_name, memory_types=["working"])  # 躲开 Qdrant 依赖
self.note_tool   = NoteTool(workspace=os.path.join(_SCRIPT_DIR, f"{project_name}_notes"))
self.terminal_tool = TerminalTool(workspace=codebase_path, timeout=60)
```

三个设计要点：
1. **只注册 3 个工具就够**：`ToolRegistry` 里只有 terminal / note / memory，对应 9.2.1 的「最小可行工具集（MVTS）」。
2. **`run()` 第五步才写历史**，且 `_update_history()` 保留最近 20 条（10 轮），与 `04` 的 10 条（5 轮）不同。
3. **`self.agent.system_prompt = context`**（L137）——每轮都用 ContextBuilder 的产物**整体替换** Agent 的系统提示，这是本章「上下文工程落地」最关键的 1 行。
   ⚠️ 但这段 context 里其实只有三段恒定分区，笔记和记忆都进不去 —— 见 **P5**。

#### 单独运行本文件（PyCharm 里右键 Run）

**上游本文件没有 `load_dotenv()`**，直接跑必然报：

```
hello_agents.core.exceptions.HelloAgentsException: API密钥和服务地址必须被提供或在.env文件中定义。
```

原因：它是设计成被 `06_three_day_workflow.py` **导入**使用的（`06` 在文件头调了 `load_dotenv()`，环境变量顺带带进来）；
而框架是在 `HelloAgentsLLM.__init__` 里才 `os.getenv`（`core/llm.py:57–83`），单跑时进程里根本没有 `LLM_API_KEY`。
**本地已在文件头补上 `load_dotenv()`**，现在单独跑也能通。

另外它自带的 `main()` 上游写的是 `project_name="my_flask_app"` + `codebase_path="./my_flask_app"`。
这个坑很隐蔽：`TerminalTool.__init__` 里有 `self.workspace.mkdir(parents=True, exist_ok=True)`，
所以**不会报错**，而是静默建出一个空的 `my_flask_app/` 目录，Agent 最后去探索一个空文件夹。
本地已改为同目录下真实存在的 `codebase/`（与 `06` 一致）。实测结果：

```bash
PY=../.venv/Scripts/python.exe
$PY codebase_maintainer.py     # EXIT 0，约 110 秒，3 次 Agent 调用
```

跑完在 `demo_codebase_notes/` 留下 5 条笔记（Agent 自主创建），报告落在 `7-agent-context/maintainer_report_*.json`。

> cwd 无关性：本地把 `NoteTool` 的 workspace 和报告文件名都锚定到 `_SCRIPT_DIR`，
> 所以无论是在 `7-agent-context/` 还是在项目根启动（PyCharm 默认常是项目根），产物都落在同一个地方。

一个实测坑（别被数字误导）：
**`get_stats()["activity"]` 的计数基本不可信。** 实测跑完一次完整的自主探索——Agent 确实执行了 `ls -la`、`cat` 等多个命令，也自动创建了笔记 `note_..._0`——但 `get_stats()["activity"]` 仍返回
`{"commands_executed": 0, "notes_created": 0, "issues_found": 0}`。
根因在 `_track_tool_usage()`：它只扫 `self.agent.message_history[-10:]`，靠 `"terminal" in content` / `"note" in content` 这类**子串匹配**猜工具名；而 `notes_created` 只在 `create_note()` 便捷方法里自增，Agent 自己通过工具创建的笔记根本不计入。调试时请直接看 `note_tool.run({"action":"summary"})`，别信这个计数器。
